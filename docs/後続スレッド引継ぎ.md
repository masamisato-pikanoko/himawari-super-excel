## 変えてはいけない境界

```text
社員受付
  -> 固定文「🌻お預かりしました。今日も一日お疲れ様でした！」
  -> job_idごとに原本・画像・成果物・履歴を分離
  -> 原本SHA-256を記録し、原本を上書きしない
  -> プログラムが診断・安全修正・事実・選択肢を決定
  -> 出口AIは構造化JSONを短い自然文へ変換するだけ
  -> Google Chatへ最大2問
  -> 2件の実回答が揃った同じjob_idだけを再開
  -> 完成ファイル・hash・QA・Drive URLの存在を確認
  -> 完成リンクカードを元の案件スレッドへ配達
```

生Excel・画像一式・OCR全文を出口AIへ渡さないでください。AIは数値、質問数、選択肢、リンク、処理結果を変更できません。

## 統合時に先に固定する契約

別パーツの実装を読んだ後、推測せず次の項目を1つのversion付きjob envelopeへ対応付けます。

| 項目 | 必須内容 |
|---|---|
| 受付 | `job_id`、社員/入口ID、受付時刻、依頼文、返信先 |
| 原本 | ファイルID/パス、名前、MIME type、SHA-256 |
| 処理状態 | `received`、`processing`、`waiting_hitl`、`running`、`completed`、`needs_adapter`、`error` |
| HITL | 最大2問、stableな`question_id`/`option_id`、コメント、同じjobのresume key |
| 成果物 | 整理済み/完成ファイル、QA JSON、全シート描画、Drive URL |
| 失敗 | retry可能性、明示的error code、最後に安全に完了したcheckpoint |

片方のシステムがすでに同等フィールドを持つ場合は、別の状態管理を増やさず対応表を作ります。Googleを正本としている現行箇所を、統合だけを理由にAzureやMicrosoft 365へ即時切替しません。

## 統合後・C/D/E前の合格条件

- 5人分を同時投入してもjob/社員/原本/回答/成果物が混ざらない
- 受付応答は処理完了を待たず固定文だけを返す
- 対応形式は必ず2問、未対応形式は推測せず`needs_adapter`
- 1回答では完成せず、2回答で同じjobが1回だけ再開する
- 再送・再試行で原本上書き、完成品二重生成、Chat二重完了が起きない
- 完成品、hash、QA、Drive URLが揃う前に完成通知を出さない
- Google Chatの質問、コメント、回答Sheet、再開キュー、完成リンクが一致する
- 全シート描画、式エラー、画像/drawing/chart/macro/external link数を検品する

## 既知の運用注意

- `clasp`が`invalid_grant` / `invalid_rapt`になったら、ローカル検証は続行し、配達/デプロイ地点で再認証する。
- `clasp run`の`NOT_FOUND`はGASエディタの通常の実行ボタンへ切り替える。
- GASはエディタ、`/dev`、本番deploymentが別物。ソースだけでなく本番と実画面を確認する。
- ChatのHTTP 200だけでは不十分。実カード、回答ボタン、元スレッド、完成リンク先まで確認する。
- 完成通知のChatアプリ経路が失敗してWebhookへ切替わる場合も、完成カードを落とさない実装がv11以降に入っている。
